# Proposed Phase 3: offline-first group scoring

**Approved architecture and acceptance gates; Stage 1 passed physical feasibility; Stage 2 was explicitly authorized and its local-draft implementation is documented in PHASE3_STAGE2.md. Stage 2 physical acceptance subsequently passed and Stage 3 was explicitly authorized; see PHASE3_STAGE3.md. Stage 4 conflict/recovery work was subsequently authorized and is documented in PHASE3_STAGE4.md. Stages 5–6 have not begun.** Phase 2 scoring rules, snapshots, revisions, idempotent operations, credential scope and permanent reveal locks remain authoritative on the server.

## Recommended scope and architecture

- **Offline-capable app shell:** a same-origin service worker caches versioned static assets after an initial online visit. First prove that the private Sites host permits the required worker scope, asset caching and offline launch on iPad/iPhone Safari. Never cache sign-in redirects or authentication routes. Preserve owner-private hosting. If the host cannot support this, report the constraint before selecting another host or changing access.
- **Durable local store:** IndexedDB holds versioned round/group snapshots, accepted score revisions, separate pending drafts, and an ordered outbox. Scope everything by backend URL, event and group credential. Keep public result projections separate from the scorer's private records so cached holes 16–18 never enter an unrevealed public leaderboard/scorecard. Mark cached public views with last-sync time; do not invent final rankings from pending scores.
- **Online preparation:** require one online PIN verification and server-confirmed course/handicap snapshot before a group goes offline. Recommend retaining that group's scoped bearer session on the trusted device for the round, surviving tab closure, with server expiry/rotation still enforced. Never save the PIN or strong admin secret. Offer an explicit forget-round/device action and clear scoped data on sign-out/reset. Durable storage changes the current same-tab session behavior; trusted-device retention is implemented in Stage 2, with server expiry/rotation still authoritative.
- **Durable scoring outbox:** each save has a stable operation ID and dependency on the last acknowledged player/hole revision. Persist before showing 'saved on this device'. Freeze request payload and ID before its first network send; replay unchanged after lost responses. Resolve earlier pending operations before sending dependent corrections. Unsent drafts may be edited locally, but sent/accepted operations are never silently rewritten or assigned new identities.
- **Foreground synchronization:** sync on reconnect, app resume and explicit Retry, one ordered stream per group with bounded backoff. Treat actual requests as the connectivity signal; do not rely on navigator.onLine, iOS Background Sync, or the app continuing to run after Safari suspension. The server confirms acceptance and remains the source of totals/history.
- **Conflict and identity recovery:** stale revisions require visible review against the latest accepted score, with correction reasons preserved. Do not silently overwrite, rebase, or impersonate another credential. Plan a narrowly scoped authenticated operation-status read for lost responses; after PIN rotation/expiry, recover any accepted old operation before authorizing a new reviewed submission. Keep the existing credential-based audit identity, not a claimed individual identity.
- **Online-only administration:** setup, group changes, credential issuance/rotation, competition draws, explicit group completion and final reveal stay online. Drain the active device's queue before Finish Group and use existing server completion/reveal validation. No server can prove that every disconnected device has uploaded its drafts: admin must confirm scorer synchronization before reveal. If a queued change arrives after a permanent reveal, reject it and retain the local pending record for review/export; never unlock or silently discard it.
- **Clear status:** distinguish 'saved on this device', 'syncing', 'accepted by server', 'conflict', and 'rejected/round locked'. Quota errors, unavailable storage or a failed transaction must not claim a durable save. Offline browser storage can still be cleared/evicted; show preparation/storage failures and keep a manual recovery path.

## Proposed implementation sequence

1. **Host/Safari feasibility and acceptance contract:** verify offline shell/worker support using a separate authorized test deployment; agree device-session retention, data clearing and queue/lock behavior. No production changes.
2. **IndexedDB and local drafts:** versioned schema, transactional writes, migration tests and round/group isolation; clear pending-versus-accepted UI. Keep live server behavior intact.
3. **Outbox and reconciliation:** stable operation IDs, ordered dependencies, lost-response replay and minimal authenticated operation-status support. Preserve server revision validation and immutable accepted history.
4. **Recovery UX:** conflicts, credential rotation/expiry, quota/storage failures, reload/crash recovery, connectivity errors and explicit manual retry. Prevent duplicate Finish or incomplete-queue completion.
5. **Offline boot and cached read views:** finish the service worker/update strategy; separate filtered public caches from private group scoring caches. Keep final reveal and administrative mutations online.
6. **Isolated end-to-end acceptance:** deterministic synthetic scenarios plus physical iPad/iPhone Safari in airplane mode, network loss during saves, tab closure/suspension, relaunch, two-device conflicts, rotation, retry after acceptance, and reveal while another device has pending changes. Then seek approval for any wider pilot.

## Acceptance gates

A confirmed local save survives reload/suspension/relaunch; a replay creates exactly one accepted operation/history chain; no silent lost scores or overwritten accepted revisions; conflicts/rejections stay visible; group scopes and hidden-hole privacy hold online and offline; BLOB/split/competition calculations stay consistent with server snapshots; reveal remains irreversible. Background synchronization while Safari is closed is not promised. Phase 2 passing Chromium tests and the earlier physical Safari online test do not validate offline behavior.

The user approved the full proposal and trusted-device bearer-session retention, then authorized Stage 2 after reviewing the successful physical Stage 1 results. Deployment approvals remain separate. Additional accepted constraints: advance scoring immediately after a confirmed durable IndexedDB transaction (without waiting for sync); never silently clear pending scores; warn and offer recovery/export before any unsynchronized data removal; disable Finish Group until all local queued scores have server acceptance; never rely on Safari synchronizing after closure. Stage 3 synchronization is implemented as documented in PHASE3_STAGE3.md; Stage 4 is documented in PHASE3_STAGE4.md; Stages 5–6 await the next review/go-ahead; Stage 2 does not implement automatic queue synchronization or an app-wide offline shell.
