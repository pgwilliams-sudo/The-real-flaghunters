# Stage 5 readiness/update fix — prepared, not deployed

Physical iPad Safari testing showed **Prepare offline app** claiming “App assets prepared” while offline, and never showing a waiting update during the first rollout. The source used `register()` and the existing active worker as readiness evidence. Reusing a registration does not establish a new update check or verify retained assets. Startup also forgot previous readiness and displayed raw server-startup `Load failed` despite a working cached app.

The new implementation separates local cache inspection from online preparation/update checking. Startup verifies the complete eight-file static allowlist, response status/type and active registration without network requests. An offline button click performs only that inspection and explicitly states that no new preparation or update check occurred. Online use forces `registration.update()` for an existing own-scope worker and tracks the actual new installer, with a bounded wait. It does not mistake the old active worker for completion of a new install. Waiting updates remain waiting; there is no forced activation or reload.

Worker-download or asset-install failure reports an incomplete/failed check while retaining the prior cache and every saved score. A failed installer is not reported as still installing. Missing/incomplete cached assets produce a missing-readiness message. The code updates no sessions, drafts or IndexedDB schema and deletes no cache; only the existing worker's namespaced activation cleanup remains. Unsupported/denied persistent-storage requests do not change a verified asset install into a false failure; storage eviction is still explicitly possible.

Offline startup skips server initialization and directs the scorer to prepared groups, removing the misleading raw connection-failure banner in that path. Prepared-group buttons refresh after known credential invalidation or explicit forgetting, removing stale access controls without removing pending requests. These changes do not renew credentials or bypass locked rounds.

The worker VERSION is bumped from `stage5-v2` to `stage5-v3` because cached application JavaScript changed. Both diagnostic paths, the eight-file allowlist, scoring/recovery payloads, operation/resolution IDs, backend, Sheet binding and permanent-lock behavior remain unchanged. Deploy all matching application assets atomically to only the existing owner-private test Site after explicit approval. The original approved diagnostic files must be preserved. No production, main merge or Stage 6 work is authorized.

Validation includes 114 automated tests, the real Chromium HTTP/worker/cache/IndexedDB scenario, 13 phone recovery scenarios and four mobile viewports. The expanded browser case checks honest offline cache inspection with no worker fetch, readable offline startup, worker-download failure, denied CSS during a new update installation, retained prior complete cache and pending operation, a successful waiting update through the actual Prepare button, activation/tab reopen, idempotent score acceptance and unchanged diagnostic/cache/private-storage evidence. Unit coverage also tests installer failure, missing assets, ownership protection and first-install activation timing. The credential browser case checks that revoked access removes its stale prepared-group button while preserving the pending score. `git diff --check` passes. WebKit runtime is unavailable; the updated messages and waiting/failed-update behavior require another guided physical Safari run.

This patch does not fix or hide the measured 24.753-second Apps Script recovery execution against the 25-second client deadline. That investigation, earlier blank-page/history-response release blockers and physical storage-eviction limitations remain recorded. Stage 5 is NOT ACCEPTED. No deployment of this patch has been performed.
